# Индексы в базах данных

## Что такое индекс

**Индекс** — вспомогательная структура данных, которая ускоряет поиск строк в таблице по значению одного или нескольких столбцов.

Аналогия: оглавление в книге. Вместо того чтобы читать всю книгу от корки до корки, вы смотрите в оглавление и сразу переходите к нужной странице.

Без индекса СУБД выполняет **полное сканирование таблицы** (Seq Scan) — просматривает каждую строку. С индексом она может быстро найти нужные строки по «указателям».

---

## Зачем нужны индексы

Индексы ускоряют:

- `WHERE` — фильтрацию по условию
- `JOIN` — соединение таблиц по ключу
- `ORDER BY` — сортировку
- `GROUP BY` — группировку (если порядок совпадает с индексом)
- проверку уникальности (`UNIQUE`, `PRIMARY KEY`)

---

## Цена использования индексов

Индекс — не бесплатное ускорение. За него платят:

| Плюс | Минус |
|------|-------|
| Быстрый поиск | Медленнее `INSERT`, `UPDATE`, `DELETE` (индекс тоже нужно обновлять) |
| Быстрая сортировка | Дополнительное место на диске |
| Быстрые JOIN | Накладные расходы на обслуживание при массовых загрузках |

**Правило:** индексируйте столбцы, по которым часто **читают** (фильтруют, сортируют, соединяют), а не те, которые постоянно **перезаписывают**.

---

## Как СУБД выбирает, использовать индекс или нет

PostgreSQL строит **план выполнения запроса** и сам решает, выгоден ли индекс.

Проверить план:

```sql
EXPLAIN SELECT * FROM products WHERE category = 'Смартфоны';
EXPLAIN ANALYZE SELECT * FROM products WHERE category = 'Смартфоны';
```

- `EXPLAIN` — показывает план без выполнения
- `EXPLAIN ANALYZE` — выполняет запрос и показывает реальное время

Типичные узлы плана:

| Узел | Что означает |
|------|--------------|
| `Seq Scan` | Полное сканирование таблицы (индекс не используется) |
| `Index Scan` | Поиск через индекс + чтение строк из таблицы |
| `Index Only Scan` | Данные берутся только из индекса (самый быстрый вариант) |
| `Bitmap Index Scan` | Индекс собирает набор строк, затем читает их пакетом |

---

## Какие индексы создаются автоматически

В PostgreSQL индекс создаётся автоматически для:

- `PRIMARY KEY` — уникальный индекс на ключевом столбце
- `UNIQUE` — уникальный индекс на столбце (или группе столбцов)

```sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,   -- индекс создаётся автоматически
    sku TEXT UNIQUE          -- индекс создаётся автоматически
);
```

---

## Создание индекса вручную

```sql
CREATE INDEX idx_products_category ON products(category);
```

Удаление:

```sql
DROP INDEX idx_products_category;
```

## Составные (композитные) индексы

**Составной индекс** — один индекс сразу на несколько столбцов. Данные внутри него отсортированы сначала по первому столбцу, затем по второму, затем по третьему и т.д.

```sql
CREATE INDEX idx_products_category_price ON products(category, price);
```

Аналогия — телефонный справочник: сначала фамилия, внутри одной фамилии — имена. Чтобы быстро найти «Иванов Иван», нужен порядок «фамилия → имя», а не наоборот.

### Зачем нужны

Один составной индекс вместо нескольких простых, когда запросы **часто фильтруют или сортируют сразу по нескольким полям**:

```sql
-- Типичный запрос в интернет-магазине
SELECT title, price
FROM products
WHERE category = 'Смартфоны' AND price BETWEEN 50000 AND 100000
ORDER BY price;
```

Индекс `(category, price)` покрывает и фильтр, и сортировку.

### Правило левого префикса

Составной индекс `(A, B, C)` работает как набор вложенных индексов:

- `(A)`
- `(A, B)`
- `(A, B, C)`

Но **не** работает как отдельные индексы на `(B)`, `(C)` или `(B, C)`.

| Индекс `(category, price, stock)` | Будет использован? |
|-----------------------------------|--------------------|
| `WHERE category = 'Смартфоны'` | ✅ Да |
| `WHERE category = 'Смартфоны' AND price > 50000` | ✅ Да |
| `WHERE category = 'Смартфоны' AND price > 50000 AND stock > 0` | ✅ Да |
| `WHERE price > 50000` | ❌ Нет (нет условия по `category`) |
| `WHERE stock > 0` | ❌ Нет (пропущен левый столбец) |
| `WHERE price > 50000 AND stock > 0` | ❌ Нет |

PostgreSQL **не «перескакивает»** через столбцы в середине индекса. Если в запросе нет условия по первому столбцу, индекс обычно бесполезен.

**Исключение:** иногда индекс всё же используют через `Bitmap Index Scan`, когда PostgreSQL объединяет несколько индексов. Но рассчитывать на это не стоит — проектируйте индекс под реальный запрос.

### Порядок столбцов: как выбрать

Столбцы в составном индексе перечисляют **слева направо по убыванию полезности для запроса**.

**1. Сначала — столбцы с точным сравнением (`=`).**

```sql
-- Хорошо: status фильтруется точно, created_at — диапазон
CREATE INDEX idx_orders_status_date ON orders(status, created_at);

-- Запрос использует индекс эффективно:
SELECT * FROM orders
WHERE status = 'paid' AND created_at >= '2025-01-01';
```

**2. Столбцы с диапазоном (`>`, `<`, `BETWEEN`) — после точных.**

Если первым в индексе стоит столбец с диапазоном, «хвост» индекса для следующих столбцов уже не сужает выборку так же эффективно.

```sql
-- Менее удачно для запроса выше:
CREATE INDEX idx_orders_date_status ON orders(created_at, status);
```

**3. Столбец с высокой селективностью — раньше.**

Селективность — насколько сильно условие сужает результат. Пол «М/Ж» (2 значения) менее селективен, чем `email` (почти уникален).

```sql
-- Лучше: сначала user_id (много уникальных значений), потом status
CREATE INDEX idx_logs_user_status ON logs(user_id, status);
```

**4. Столбцы из `ORDER BY` — в том же порядке, что и в запросе.**

```sql
CREATE INDEX idx_products_cat_price ON products(category, price);

-- Индекс поможет и фильтру, и сортировке:
SELECT title FROM products
WHERE category = 'Ноутбуки'
ORDER BY price DESC;
```

### Составной индекс и ORDER BY

Индекс `(A, B)` может избавить от отдельной операции сортировки, если:

- есть условие по `A` (или `A` — константа в контексте запроса);
- `ORDER BY` идёт по `A`, затем по `B` (или только по `B` при фиксированном `A`);
- направление сортировки совпадает (`ASC` / `DESC`) или PostgreSQL может просканировать индекс в обратном порядке.

```sql
-- Индекс (category, price) ускорит:
SELECT title FROM products
WHERE category = 'Смартфоны'
ORDER BY price;           -- сортировка по второму столбцу индекса

-- Но не поможет:
SELECT title FROM products
WHERE category = 'Смартфоны'
ORDER BY title;           -- title нет в индексе
```

### Уникальный составной индекс

Комбинация столбцов может быть уникальной, даже если каждый столбец по отдельности — нет:

```sql
-- Один пользователь не может дважды оценить одну книгу
CREATE UNIQUE INDEX idx_rating_unique ON book_ratings(book_id, reader_id);
```

Это одновременно ограничение целостности и индекс для быстрого поиска по паре `(book_id, reader_id)`.

### Составной vs несколько простых индексов

| Подход | Когда подходит |
|--------|----------------|
| `(category, price)` | Запросы почти всегда фильтруют по `category`, иногда ещё и по `price` |
| `(category)` + `(price)` | Запросы часто идут **только** по `category` или **только** по `price` |
| `(category, price)` вместо `(category)` | Если есть `(category, price)`, отдельный `(category)` обычно **не нужен** — левый префикс уже покрывает |

```sql
-- Избыточно: второй индекс дублирует левую часть первого
CREATE INDEX idx_cat ON products(category);
CREATE INDEX idx_cat_price ON products(category, price);  -- достаточно только этого
```

Если же запросы бывают и по `category`, и только по `price` — одного `(category, price)` мало, нужен ещё индекс на `price`.

### Сколько столбцов включать

- **2–3 столбца** — нормальная практика.
- **4 и больше** — только если запросы реально используют всю цепочку; иначе индекс раздувается и дороже обновляется.
- Каждый новый столбец увеличивает размер индекса и стоимость `INSERT`/`UPDATE`.

Не добавляйте столбец в индекс «на всякий случай» — только если он участвует в `WHERE`, `JOIN` или `ORDER BY` типичных запросов.

### Примеры из практики

```sql
-- Заказы: фильтр по пользователю + сортировка по дате
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC);

-- Склад: категория + наличие
CREATE INDEX idx_products_cat_stock ON products(category, stock)
WHERE stock > 0;   -- составной + частичный

-- Логи: поиск по типу события и времени
CREATE INDEX idx_events_type_time ON events(event_type, created_at);
```

### Частые ошибки с составными индексами

| Ошибка | Почему плохо | Что делать |
|--------|--------------|------------|
| `(price, category)` вместо `(category, price)` | Запрос `WHERE category = ...` не использует индекс | Первым — столбец из обязательного `WHERE` |
| Индекс на 5 столбцов «под все запросы» | Большой, медленно обновляется, редко полностью используется | Несколько узких индексов под разные запросы |
| Дублировать `(a)` и `(a, b)` | Лишнее место и замедление записи | Оставить только `(a, b)` |
| Ждать ускорения `WHERE b = 1` от индекса `(a, b)` | Нарушено правило левого префикса | Создать отдельный индекс на `b` или перестроить запрос |

## Виды индексов (общая классификация)

### 1. По количеству столбцов

| Тип | Описание | Пример |
|-----|----------|--------|
| **Простой** | Один столбец | `CREATE INDEX ON products(category)` |
| **Составной (композитный)** | Несколько столбцов в одном индексе | `CREATE INDEX ON products(category, price)` |

Подробнее — в разделе [Составные индексы](#составные-композитные-индексы) выше.

### 2. По уникальности

| Тип | Описание |
|-----|----------|
| **Обычный** | Ускоряет поиск, дубликаты допустимы |
| **Уникальный** | Ускоряет поиск + запрещает дубликаты (`CREATE UNIQUE INDEX`) |

### 3. По охвату строк

| Тип | Описание |
|-----|----------|
| **Полный** | Индексирует все строки таблицы |
| **Частичный (partial)** | Только строки, удовлетворяющие условию `WHERE` |

```sql
-- Индексируем только товары в наличии — экономим место
CREATE INDEX idx_in_stock ON products(title) WHERE stock > 0;
```

### 4. По выражению

**Индекс по выражению** — индексируется не столбец напрямую, а результат функции или выражения.

```sql
CREATE INDEX idx_lower_email ON users(LOWER(email));
```

Полезно, когда в запросах часто пишут `WHERE LOWER(email) = 'anna@mail.ru'`.

### 5. Покрывающий индекс (INCLUDE)

В PostgreSQL можно добавить столбцы «для чтения», не включая их в ключ поиска:

```sql
CREATE INDEX idx_category_cover ON products(category) INCLUDE (title, price);
```

Это повышает шанс на `Index Only Scan` — когда СУБД не обращается к самой таблице.

## Типы индексов в PostgreSQL

PostgreSQL поддерживает несколько **методов индексации** (access methods). При создании индекса можно указать тип через `USING`:

```sql
CREATE INDEX idx_name ON table_name USING btree(column);
```

Если `USING` не указан — по умолчанию используется **B-tree**.

### B-tree (по умолчанию)

**Самый универсальный и частый тип.**

Подходит для:

- сравнений: `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`
- сортировки `ORDER BY`
- `IS NULL` / `IS NOT NULL`
- шаблонов `LIKE 'abc%'` (если нет ведущего `%`)

Используйте B-tree, если не уверены, какой тип нужен.

```sql
CREATE INDEX idx_products_category ON products USING btree(category);
```

### Hash

Оптимизирован только для **точного сравнения** (`=`).

- не поддерживает диапазоны (`>`, `<`)
- не поддерживает сортировку
- на практике используется редко; B-tree обычно предпочтительнее

```sql
CREATE INDEX idx_products_sku ON products USING hash(sku);
```

### GIN (Generalized Inverted Index)

«Инвертированный» индекс — хорошо работает, когда **одно значение в строке содержит много элементов**.

Подходит для:

- полнотекстового поиска (`tsvector`)
- массивов (`INTEGER[]`, `TEXT[]`)
- `JSONB` (поиск по ключам и значениям)
- составных типов

```sql
CREATE INDEX idx_tags ON articles USING gin(tags);
CREATE INDEX idx_data ON events USING gin(payload jsonb_path_ops);
```

### GiST (Generalized Search Tree)

Универсальное дерево для **сложных типов данных и геометрии**.

Подходит для:

- геоданных (точки, полигоны, «рядом со мной»)
- диапазонов (`daterange`, `int4range`)
- полнотекстового поиска (альтернатива GIN)
- пользовательских типов

```sql
CREATE INDEX idx_location ON places USING gist(coordinates);
```

### SP-GiST (Space-Partitioned GiST)

Для **разреженных и неоднородных** данных: деревья, сетки, разбиение пространства.

Примеры: IP-адреса, точки на плоскости с неравномерным распределением.

```sql
CREATE INDEX idx_ip ON logs USING spgist(ip_address inet_ops);
```

### BRIN (Block Range Index)

Индексирует **диапазоны блоков** таблицы, а не каждую строку.

Подходит для:

- очень больших таблиц (миллионы и миллиарды строк)
- данных с естественным порядком (дата, timestamp, автоинкрементный id)
- ситуаций, где важен минимальный размер индекса

```sql
CREATE INDEX idx_created_at ON events USING brin(created_at);
```

BRIN маленький и дешёвый в обслуживании, но менее точный, чем B-tree.

### Bloom (расширение)

Вероятностный индекс для **фильтрации по нескольким столбцам одновременно**.

- требует расширение `bloom`
- может давать ложноположительные срабатывания (но не пропускает нужные строки)
- используется в специфических сценариях, не в повседневной разработке

---

## Сводная таблица: какой тип выбрать

| Задача | Тип индекса в PostgreSQL |
|--------|--------------------------|
| Фильтр, сортировка, диапазоны | **B-tree** (по умолчанию) |
| Точное сравнение `=` на огромной таблице | Hash (редко) или B-tree |
| Полнотекстовый поиск | **GIN** или GiST |
| JSONB, массивы | **GIN** |
| Геоданные, «рядом», пересечения | **GiST** или SP-GiST |
| Огромная таблица с датами / id по порядку | **BRIN** |
| Несколько столбцов в одном фильтре | Составной B-tree или Bloom |

## Когда индекс **не** поможет

1. **Маленькая таблица** — полное сканирование может быть быстрее, чем обращение к индексу.
2. **Низкая селективность** — столбец с 2–3 уникальными значениями (пол, статус «да/нет»). Индекс почти не сужает выборку.
3. **Функция над столбцом** — `WHERE LOWER(name) = 'anna'` не использует обычный индекс на `name`. Нужен индекс по выражению.
4. **Ведущий символ `%` в LIKE** — `LIKE '%phone'` не использует B-tree (в отличие от `LIKE 'phone%'`).
5. **Слишком много индексов** — каждая запись обновляет все индексы таблицы.
6. **Нерелевантный составной индекс** — неправильный порядок столбцов или лишние столбцы.

---

## Типичные ошибки и как их избежать

| Ошибка | Решение |
|--------|---------|
| Индекс на каждый столбец «на всякий случай» | Индексируйте только столбцы из реальных запросов |
| Индекс на столбец, который часто обновляется | Пересмотрите необходимость или используйте частичный индекс |
| Ожидание ускорения `SELECT *` | Индекс помогает найти строки, но чтение всех столбцов всё равно дорого |
| Не смотрят `EXPLAIN` | Всегда проверяйте план на медленных запросах |
| Дублирующие индексы | `(a)` и `(a, b)` — первый часто избыточен, если есть второй |

---

## Практические рекомендации

1. **Начинайте с B-tree** — он покрывает 90% задач.
2. **Индексируйте внешние ключи** (`FOREIGN KEY`) — они часто участвуют в `JOIN`.
3. **Составной индекс** — первым ставьте столбец с наиболее строгим фильтром.
4. **Частичный индекс** — если запросы всегда содержат одно и то же условие (`WHERE is_active = TRUE`).
5. **Проверяйте план** через `EXPLAIN ANALYZE` до и после создания индекса.
6. **Не создавайте индекс до появления реальной проблемы** — преждевременная оптимизация усложняет схему.

## Полезные команды PostgreSQL

```sql
-- Список индексов таблицы
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'products';

-- Размер индексов
SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE relname = 'products';

-- Пересоздать статистику (помогает планировщику)
ANALYZE products;
```

## Краткий итог

- **Индекс** ускоряет чтение, но замедляет запись и занимает место.
- В PostgreSQL по умолчанию — **B-tree**; он подходит для большинства задач.
- **Составной индекс** `(A, B, C)` работает по **правилу левого префикса** — порядок столбцов критичен.
- Сначала в индекс ставят столбцы с `=`, затем с диапазоном; не дублируйте `(a)`, если уже есть `(a, b)`.
- Специализированные типы (**GIN**, **GiST**, **BRIN**) — для полнотекстового поиска, JSONB, геоданных и очень больших таблиц.
- Индекс нужно подбирать под **конкретные запросы**, а не создавать «на всё».
- Инструмент проверки — **`EXPLAIN ANALYZE`**.
